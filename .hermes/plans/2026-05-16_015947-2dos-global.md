# Plan de implementación — 2dos-global.md

## Goal
Implementar de forma incremental los pendientes definidos en `2dos-global.md` para evolucionar la pestaña ESTRATEGIA hacia un flujo completo de backtesting, optimización, carga de datos externos, métricas y mejoras de UX.

## Current context / assumptions
- Proyecto sin build system (HTML/JS/CSS puro).
- Archivos clave esperados:
  - `index.html`
  - `frontend/js/modules/indicators.js`
  - `backend/server.js`
- La app usa WebSocket de Deriv para datos en tiempo real.
- `2dos-global.md` define 5 fases con prioridad/área/esfuerzo.
- Notas técnicas del backlog:
  - `estrMarks` vive en memoria (sin persistencia).
  - Indicadores se recalculan completos en cada actualización.
  - Estrategias backend no están conectadas con la UI.

## Proposed approach
1. Ejecutar por fases, priorizando `@priority:high` y desbloqueando dependencias técnicas primero.
2. Definir un “Strategy Engine Contract” común entre frontend y backend (input de velas + params, output de señales normalizadas).
3. Implementar primero visibilidad y validación (botón backtest + markers + comparativa) antes de optimizador/métricas avanzadas.
4. Añadir persistencia/import-export de marcas antes de optimización intensiva para no perder ground truth.
5. Cerrar con mejoras UX y performance (memoización) tras tener flujo base estable.

## Step-by-step plan

### Fase 0 — Preparación técnica (prerrequisito)
1. Inventariar estado actual de pestaña ESTRATEGIA, estructura de `dataHistory`, formato de `estrMarks`, y flujo de dibujo de markers.
2. Definir contrato único de señal:
   - Campos mínimos: `time`, `type` (CALL/PUT), `price`, `strategyId`, `params`, `source`.
3. Elegir puente frontend-backend para estrategias:
   - Opción recomendada: endpoint REST en `backend/server.js` para backtest por lote.
   - Alternativa: ejecución directa en frontend replicando lógica (menos deseable por duplicación).
4. Crear checklist de compatibilidad de timestamps (epoch/segundos/milisegundos) para evitar desalineación de velas.

### Fase 1 — Backtest automatizado (prioridad alta)
5. Integrar estrategias en la pestaña ESTRATEGIA con selector y parámetros visibles/editables.
6. Añadir botón `Ejecutar backtest` en toolbar:
   - Ejecuta estrategia sobre todo `dataHistory`.
   - Renderiza señales automáticas con markers translúcidos en chart de análisis.
7. Implementar comparativa señales automáticas vs manuales:
   - Tabla por vela/manual mark: match exacto temporal, match por dirección, omisiones, falsos positivos.
   - Métricas resumidas: aciertos, fallos, omisiones, FPs.
8. Añadir tolerancia configurable de alineación temporal (si timeframe/normalización introduce offsets).

### Fase 2 — Optimización de parámetros
9. Implementar escaneo de parámetros por rangos (grid search inicial):
   - Ejemplo: RSI period 5–21, SMA 10–50.
10. Definir función objetivo (score): prioridad a precisión sobre marcas manuales + penalización por FPs.
11. Mostrar resultados en tabla ordenable (heatmap opcional en segunda iteración).
12. Añadir controles para limitar combinaciones (evitar bloqueos UI): batch size, máximo iteraciones, cancelación.
13. Integrar export/import JSON de `estrMarks` (incluyendo `time,type,price,indicator values`).

### Fase 3 — Carga de datos externos
14. Añadir carga CSV (`time,open,high,low,close`) en pestaña ESTRATEGIA:
   - Validación estricta de esquema.
   - Normalización de tiempo y ordenado ascendente.
   - Reemplazo explícito de `dataHistory` con confirmación UX.
15. Añadir caché offline de `dataHistory` (localStorage o IndexedDB):
   - Estrategia recomendada: IndexedDB para volúmenes grandes.
   - Fallback opcional localStorage para datasets pequeños.
16. Añadir selector de fuente de datos activa (live/csv/cache).

### Fase 4 — Métricas de rendimiento
17. Implementar dashboard de métricas:
   - win rate, profit factor, reward/risk, Sharpe (simplificado), drawdown máximo, nº operaciones.
18. Definir supuestos de PnL (riesgo fijo, payout estimado, coste/spread si aplica).
19. Implementar equity curve acumulada y sincronizar con selección de estrategia/params.

### Fase 5 — UX / Calidad de vida
20. Habilitar borrado de marca por click directo en marker del chart.
21. Tooltip de análisis con snapshot de indicadores por vela.
22. Opción de sincronizar zoom/scroll trading↔análisis.
23. Revisión de rendimiento:
   - Memoización en `updateAnalysisIndicators()`.
   - Throttling/debounce en eventos de interacción.

### Fase 6 — Endurecimiento y cierre
24. Pruebas manuales integrales por escenario:
   - Live WS
   - CSV offline
   - Cache restore
   - Backtest + comparativa + métricas
25. Documentar formatos de datos, límites y troubleshooting en README/sección técnica.

## Files likely to change
- `index.html` (UI: toolbar, botones, paneles, tablas, tooltips)
- `frontend/js/modules/indicators.js` (cálculos y posible memoización)
- `frontend/js/...` (módulos de estrategia, render de markers, tabla comparativa, parser CSV, cache, métricas)
- `backend/server.js` (endpoint(s) para ejecución de estrategias/ backtest si se usa puente backend)
- `backend/strategies/...` (normalización/adaptación de salida de señales)
- `2dos-global.md` (actualización de estado de tareas)

## Tests / validation
- Validación funcional manual por cada historia de usuario del backlog.
- Verificar alineación temporal exacta entre:
  - velas,
  - marcas manuales,
  - señales de estrategia.
- Verificar no regresión en flujo actual de gráficos e indicadores.
- Dataset de prueba mínimo y dataset grande para performance.
- Casos borde CSV:
  - columnas faltantes,
  - timestamps inválidos,
  - filas desordenadas/duplicadas.
- Verificar persistencia (export/import/cache) con recarga completa de página.

## Risks, tradeoffs, open questions
- Riesgo: desalineación de timestamps entre fuentes (WS/CSV/cache) puede falsear métricas.
- Riesgo: grid search grande bloquea UI si se ejecuta en main thread.
- Tradeoff: backend centraliza lógica (consistencia) vs frontend directo (latencia/despliegue simple).
- Tradeoff: localStorage simple vs IndexedDB escalable.
- Preguntas abiertas:
  1. ¿La verdad terreno (ground truth) son solo marcas manuales o habrá dataset etiquetado externo?
  2. ¿Qué supuestos exactos de payout/coste usar para métricas financieras?
  3. ¿Se requiere paridad exacta de estrategias backend en frontend o una sola fuente de verdad?
  4. ¿Límite objetivo de velas para optimización interactiva en UI?
